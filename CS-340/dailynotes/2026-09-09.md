# More TS

## Type aliasing literals

Remember: **TS treats constants as their own type.**

```ts
// chess
type Color = 'Black' | 'White'
type File = 'A' | 'B' | 'C' | 'D' | 'E' | 'F' | 'G' | 'H'
type Rank = 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8
```

## Classes

Some history: TS added classes before CS did.

- The name of the constructor is `constructor()`
- Default member visibility is public.
- Use `super` to call superclass methods.
  - In particular, call <code>super(&hellip;)</code> in the constructor to call the superclass's constructor.
- Only single inheritance is allowed in TS. (Classes can only inherit from one class.)
- You can make members `static`, meaning they're shared across all instances of the class.
  - Static members can be accessed from the class without needing an instance for it. e.g., 
    - (You have to use the name of the class even within the class itself. `this` won't work.)
- `implements` is the keyword for a class "inheriting" an interface. You can implement as many interfaces as you'd like.
- Subclasses cannot change visibility of a member it inherits or implements.

### EXAMPLE

```TS
// chess
type Color = 'Black' | 'White'
type File = 'A' | 'B' | 'C' | 'D' | 'E' | 'F' | 'G' | 'H'
type Rank = 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8

class Position {
  public constructor(private file: File, private rank: Rank) {}

  public distanceFrom(position: Position) { rank: number, file: number } {
                                        /* ^ return type */
    return {
      rank: Math.abs(position.rank - this.rank),
      file: Math.abs(position.file.charCodeAt(0) - this.file.charCodeAt(0))
    }
  }
}
```

### Abstract classes

You can define an abstract class with `abstract class`, and then within it define abstract methods with <code>public|protected|private abstract <i>funcName</i>(&hellip;) { &hellip; } </code>.

Classes that inherit from an abstract class without overriding its abstract methods are necessarily also abstract.

### Getters/setters

One of the useful things about getters/setters ("accessors"/"mutators") is that if you start a variable out as `public`, you can easily convert it to `private` or `protected` and all the syntax treating it like its public will still work just fine.

### Structural typing

Most languages base the type compatibility on the names of the type. e.g., in Java, if you have two classes with the exact same source code but different class names, they would not be compatible with each other. TS is the opposite.

Is that a good thing? Who knows. It's kind of necessary though because TS has to match some of the flexibility of JS.

For a class `T1` to be compatible with `T2`, it has to be either identical or a superset of the other.

```ts
class Zebra {
  trot() { /* ... */ }
}

class Poodle { 
  trot() { /* ... */ }
}

function ambleAround(animal: Zebra) {
  animal.trot()
}

let zebra = new Zebra;
let poodle = new Poodle;
let donkey = { trot: () => { /* ... */ }, 
               heehaw: () => { /* ... */ } };

ambleAround(zebra); // OK
ambleAround(poodle); // OK
ambleAround(donkey); // OK
```

### `instanceof`

- `instanceof` queries an object to see if it is or extends a base class (directly or indirectly).
- `instanceof` can NOT be used to check if an object implements a particular *interface*.
  - `instanceof` is a runtime operation. Interfaces do not exist in JS, so interfaces don't exist at runtime. 

## `readonly`

### `const` vs `readonly`

- `const` means a variable can not be reassigned.
- `readonly` means a variable's value is immutable.

### `readonly` is shallow

`readonly` only affects one level. 

```ts
interface Box {
  readonly items: number[];
}

const b: Box = { items: [1, 2] };
b.items = []; // ERR
b.items.push(3); // OK
```

### `readonly` arrays/tuples

```ts
let a: readonly number[] = [1, 2, 3];

let three = a[2]; // OK
a[2] = 5; // ERR
a.push(6); // ERR
```

### Inheritance/interfaces w/ `readonly` properties

- Subclasses cannot make a superclass's `readonly` member non-`readonly`.

## Defining "object shapes" w/ type aliases and interfaces

You can cast a typeless JS object (e.g., when loading JSON) to a type alias or an interface. 

Why do both exist? Originally, TS just had interfaces. Later, they added type aliases. Type aliases are more general and can do more things, but interfaces are better in a few places. 


### Better type-checking when extending interfaces

Interfaces do a bit better w/ type checking when they're extended. I.e., **interfaces work better w/ polymorphism**.

```ts
// extending a type alias
type A = {
  one(x: number): string
  two(x: number): string
}

type B = A & {
  one(x: string | number): string
  one(x: string): string 
      // ^ fails silently
}
```

```ts
// extending an interface
interface A { 
  one(x: number): string
  two(x: number): string
}

interface B extends A {
  one(x: string | number): string
  bad(x: string) : string
        // ^ Error TS2430
}
```

### Interface unions

This doesn't work:

```ts
type User = { 
  name: string
}

type User = {
  age: number
}
```

It tries to redefine `User`. 

But this does work:

```ts
interface User {
  user: string
}

interface User {
  age: number
}

let a: User = {
  name: "Caleb",
  age: 67
};
```

Instead of redefining `User`, it adds to it.
